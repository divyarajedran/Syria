Implementation plan — what each page becomes

The UI pattern each current page converts to. The goal is to keep the user on one surface: a page is a full workspace only when it's a landing; most “screens” become a tab, a right drawer, a modal, a bottom sheet, a step in a guided flow, or a persistent bar.

WORKSPACE role landing (full page) TAB section inside a workspace/object DRAWER slide-in right pane MODAL focused create/edit overlay SHEET mobile bottom sheet FLOW multi-step wizard, one surface BAR persistent action bar CARD status card, drill-in on demand CONFIRM inline confirm, no page

Rule of thumb: a current page stays a full page only if it's a role's landing or a standalone object (the call, a public verify link). Everything a user does to a row — edit, book, bill, approve, respond, set status — becomes a drawer, modal or inline confirm so they never lose their place in the list.

Development plan & tracker

Six phases, ordered so every phase ships something usable and the risky work (inline actions, guided flows) comes after the low-risk regrouping. Set a status and owner on each task; progress rolls up per phase and overall. Estimates are working days for one developer and are meant for sequencing, not commitment.

Dependencies & risks to manage

ItemWhy it mattersMitigation
Menus are generated from the plan DBRe-nesting the menus in code is undone by the next regeneration.Write the new workspace structure into plan_menu_route in the same change (task P0-5).
Role-to-workspace permissionsA workspace shows only if the role can use something inside it; SYSADM bypass is still deferred.Derive visibility from existing permissions; enforce routes in P5-1 rather than relying on hidden menus.
Drawers and modals on small screensA right pane does not fit a phone or narrow tablet.Same component renders as a bottom sheet under a width breakpoint (P0-2, P5-3).
Live calls must not dropOpening an action must never leave the call room (the care-team overlay already proved this).Every in-call action is an overlay or drawer, never a route change.
Old and new UI running togetherStaff need a safe way back during rollout.Per-app workflow_ui flag (P0-3) and redirects from old routes (P1-9).
Each phase needs a redeployDeployed builds lag local changes; the front-end and API deploy separately.Treat each phase exit as a release with its own smoke test (P5-4).
